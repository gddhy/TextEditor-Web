## PWA Window Controls Overlay 修复（继续 08-01 项目）

### 问题
PWA 安装后 Windows 在右上角画最小化/最大化/关闭系统按钮，把应用自己的按钮（新建/打开/保存/下载/...）遮挡。

### 解决（3 步）
1. **CSS**（`css/app.css`）：`.appbar` 加
   ```css
   padding-right: calc(env(titlebar-area-width, 0px) + env(safe-area-inset-right, 0px));
   ```
   普通浏览器 tab 模式下 `titlebar-area-width` 默认为 0px，**视觉无变化**；安装后 PWA 模式自动让出系统控件宽度。
2. **JS**（`js/app.js`）：新增 `setupWindowControlsOverlay()`，
   - 检查 `'windowControlsOverlay' in navigator`
   - 监听 `geometrychange`（最大化/还原/缩放窗口时重读 `getTitlebarAreaRect()`）
   - 切换 `<html class="wco">` 和 `.appbar.wco-tall`
   - 在 `startApp()` 里调用
3. **SW 版本**：`text-editor-v2` → `text-editor-v3`（不 bump 的话已装 PWA 仍跑旧 CSS/JS，看不见修复效果）

### 关键发现
- `manifest.json` 已经声明了 `"display_override": ["window-controls-overlay", "standalone", "browser"]`，无需改 manifest
- 单纯改 CSS 不够：env() 在最大化/还原时不会自动更新，需要 JS 监听 `geometrychange` 同步切换 class
- `env(safe-area-inset-right)` 是兜底（处理 macOS 等其他系统的不安全区）

### 验证
- 普通浏览器标签页：`env()` 解析为 0px，布局不变
- 安装 PWA（window-controls-overlay 模式）：应用按钮自动左移避开系统控件
- 拖动：`.appbar` 的 `-webkit-app-region: drag` 已存在，标题栏空白处仍可拖动窗口

## 第二轮：让系统按钮颜色与 appbar 一致

### 问题
让位后系统按钮区域是紫色（manifest `theme_color`=#6750A4），appbar 是浅紫（`--md-surface-c`=#F3EDF7），色差仍突兀。

### 根因
Chrome 在 window-controls-overlay 模式下用 `theme_color` 给系统按钮区域填底色；CSS 无法覆盖 OS 绘制的控件。

### 解法（让 theme_color 跟着 appbar 走）
- `manifest.json` `theme_color: #6750A4 → #F3EDF7`（匹配亮色 appbar）
- `manifest.json` `background_color: #141218 → #F3EDF7`（消除启动闪烁）
- `index.html` meta `theme-color` 亮色 `#6750A4 → #F3EDF7`、暗色 `#141218 → #211F26`（跟随对应 appbar）
- `sw.js` `v3 → v4`（manifest 也被 SW 缓存）

### 效果
- 系统按钮区域变为浅紫，与 appbar 无缝衔接
- Chromium 因对比度自动把系统按钮图标改成深色，视觉一致
- 浏览器地址栏（非 PWA 模式）也变浅紫，品牌色靠 logo 维持

### 已知限制
- 安装后的 PWA，manifest `theme_color` 是单一值，**不会跟随系统亮/暗主题切换**
- 暗色模式下 PWA 系统按钮区域仍为浅紫；非安装状态（meta theme-color）会按 `prefers-color-scheme` 切换

## 第三轮：WCO 模式下让 appbar 也跟着 theme_color 走

### 问题
第一轮只改了 `theme_color` 没用：`theme_color` 是 manifest 里的**固定值**，安装后的 PWA 系统按钮区域永远是一个色，不会跟随系统亮暗切换。
- 亮色系统：appbar 浅紫 + 系统按钮浅紫 ✓
- 暗色系统（已装 PWA）：appbar 深色（`--md-surface-c=#211F26`）+ 系统按钮浅紫 ✗ 仍然不匹配

### 解法
CSS 加 `:root.wco` 选择器（`setupWindowControlsOverlay()` 已自动加这个 class），
强制 WCO 模式下 appbar 使用与 `theme_color` 同一个固定值 `#F3EDF7`：

```css
:root.wco .appbar {
  background: #F3EDF7;
  border-bottom-color: #CAC4D0;
}
```

普通浏览器 tab 模式不命中，appbar 仍跟随 `--md-surface-c` 双模式切换。

### 副作用
暗色系统下安装的 PWA，appbar 也是浅紫——牺牲了"暗色模式深色 appbar"的设计感，换来视觉一致性。如果用户不接受可以回退这一步。

### SW 版本
`v4 → v5`

## 第四轮（最终）：appbar 反过来用品牌色 #6750A4

### 问题（用户反馈）
上一轮让 appbar 跟随 theme_color 改成 `#F3EDF7` 后：
- 暗色 PWA：appbar 浅紫，但**已装 PWA 的系统按钮区域在用户机器上仍是 #6750A4 紫**（manifest 缓存，安装时读，卸载重装前不会更新）→ 还是有色差
- 亮色 PWA：appbar 浅紫 + 系统按钮浅紫，但 tab 区是白的，整体还是割裂
- 用户评价：「暗色搞得不一致了」+ 亮色也无变化

### 关键发现
**manifest 修改对已装 PWA 不生效**——Chrome 把 manifest 缓存到本机（安装时读）。改 manifest 文件后，已装用户**必须卸载重装**才能生效。这不可接受。

### 终极解法：让 appbar 反过来用 #6750A4（品牌紫）
- WCO 模式下 appbar 背景 = `#6750A4`（= OS 按钮区域**已装用户当前看到的实际颜色**）
- 内部元素全部调整为白色（`rgba(255,255,255,.88)` 图标、`#FFFFFF` 文字、白色 brand-mark）
- 高亮按钮（active/.toggle.on）= 白底紫字
- manifest.theme_color 恢复 `#6750A4`（保证**新**安装用户也是品牌紫；旧的也能在卸载重装后跟上）

```css
:root.wco .appbar { background: #6750A4; border-bottom-color: #6750A4; }
:root.wco .appbar-divider { background: rgba(255, 255, 255, .22); }
:root.wco .appbar-brand, :root.wco .brand-name { color: #FFFFFF; }
:root.wco .brand-mark rect { fill: #FFFFFF; }
:root.wco .brand-mark path { stroke: #FFFFFF; }
:root.wco .icon-btn { color: rgba(255, 255, 255, .88); }
:root.wco .icon-btn.active,
:root.wco .icon-btn.toggle.on { color: #6750A4; background: #FFFFFF; }
```

### 效果
- PWA 模式下（不论系统亮暗、不论已装未装）：顶部从左到右**统一品牌紫 #6750A4**，永远无反差
- 普通浏览器 tab 模式（不命中 `:root.wco`）：appbar 仍跟随 `--md-surface-c`，亮紫/暗紫不变

### 文件改动
- `css/app.css`：WCO 样式段重写
- `manifest.json`：`theme_color: #F3EDF7 → #6750A4`、`background_color` 改为 `#1D1B20`
- `index.html`：meta `theme-color` 全部回到 `#6750A4`
- `sw.js`：`v5 → v6`

## 第五轮：WCO 暗色下 appbar 跟随 OS 黑色

### 问题（用户反馈）
亮色 PWA 紫底白图标 OK，但**暗色 PWA 下 Windows 自动把系统按钮区域画成黑色**，appbar 仍是紫色 → 又割裂。

### 关键事实
- Windows 11 对 PWA `window-controls-overlay` 暗色主题下，**OS 控件区域固定黑底**，不管 manifest.theme_color 是多少
- 也就是说：暗色 PWA 想统一，appbar **必须用黑/深色**

### 解法：组合选择器
新增 `:root.wco[data-theme="dark"]` 规则（仅当 WCO 模式 + 暗色主题同时成立时生效）：

```css
:root.wco[data-theme="dark"] .appbar {
  background: #1D1B20;          /* 接近 OS 黑色但略带紫调,和 MD 暗色 surface 系列呼应 */
  border-bottom-color: #1D1B20;
}
:root.wco[data-theme="dark"] .appbar-divider { background: rgba(255, 255, 255, .14); }
:root.wco[data-theme="dark"] .appbar-brand,
:root.wco[data-theme="dark"] .brand-name { color: #E6E1E5; }
:root.wco[data-theme="dark"] .brand-mark rect { fill: #E6E1E5; }
:root.wco[data-theme="dark"] .brand-mark path { stroke: #E6E1E5; }
:root.wco[data-theme="dark"] .icon-btn { color: rgba(230, 225, 229, .88); }
:root.wco[data-theme="dark"] .icon-btn.active,
:root.wco[data-theme="dark"] .icon-btn.toggle.on { color: #1D1B20; background: #E6E1E5; }
```

主题切换通过 `document.documentElement.dataset.theme = t`（`applyTheme()` 已实现），CSS 选择器**自动响应**——不用改 JS。

### 效果
- 浏览器标签页（亮/暗）：不命中 `:root.wco`，appbar 跟随 `--md-surface-c` ✓
- PWA 亮色：命中 `:root.wco`、不命中 `[data-theme="dark"]`，appbar 品牌紫 #6750A4 ✓
- PWA 暗色：同时命中 `:root.wco[data-theme="dark"]`，appbar 深色 #1D1B20，文字图标 #E6E1E5，与 OS 黑色按钮区域一致 ✓

### SW 版本
`v6 → v7`

## 第六轮：WCO 下 brand-mark 变白色圆角矩形

### 问题（用户反馈）
PWA 安装后 appbar 里的"图标是白色圆角矩形，无法正常显示"。网页内正常。

### 根因（实测确认）
实测所有 `.icon-btn` 都正常（fill:none, stroke 浅色, ::before opacity 0, background transparent）—— 真正的"白色圆角矩形"是 **`brand-mark` logo**：

```html
<svg class="brand-mark">
  <rect x="2" y="2" width="20" height="20" rx="6"/>  <!-- 20x20 圆角矩形 -->
  <path d="M8 8h8M8 12h8M8 16h5" .../>              <!-- logo 三条线 -->
</svg>
```

我上一轮的 WCO 规则把它俩都设成了白色：
```css
:root.wco .brand-mark rect { fill: #FFFFFF; }
:root.wco .brand-mark path { stroke: #FFFFFF; }
```

→ **白色圆角矩形底 + 白色描线 = 整块就是个白色圆角矩形**，内部三条线在白底上看不见。完全匹配用户描述。

### 解法
WCO 下让 logo 保持"色块 + 对比字"的层次，块色和 appbar 区分、字色和块色对比：

```css
/* 亮色 PWA(appbar=#6750A4):深紫块 + 白字 */
:root.wco .brand-mark rect { fill: #381E72; }
:root.wco .brand-mark path { stroke: #FFFFFF; }

/* 暗色 PWA(appbar=#1D1B20):浅紫块 + 深紫字 */
:root.wco[data-theme="dark"] .brand-mark rect { fill: #D0BCFF; }
:root.wco[data-theme="dark"] .brand-mark path { stroke: #381E72; }
```

非 WCO 模式不命中，logo 仍 = `var(--md-primary)` + `var(--md-on-primary)`，不变。

### 实测验证（file:// + agent-browser + 注入 wco）
- WCO 亮色：`brandRectFill=rgb(56,30,114)`、brandPathStroke=white ✓
- WCO 暗色：`brandRectFill=rgb(208,188,255)`、brandPathStroke=深紫 ✓
- icon-btn 全部：color 浅色、background transparent、::before opacity 0 ✓（证明 icon-btn 不是问题）

## PWA Shortcuts 功能实现

### 问题
`manifest.json` 的 `shortcuts` 数组定义了两个快捷方式（新建文档 `?action=new`、新建 Markdown 文档 `?action=new&ext=md`），但点击后无效果——根因是 `js/app.js` 的 `bootstrapInitialDoc()` 没有读取 URL 查询参数。

### 实现（3 步）

#### 1. `js/app.js` `bootstrapInitialDoc()` 头部新增 URL 参数分支
```js
// 0) PWA 快捷方式 / 手动链接：?action=new[&ext=md]
var startParams = (global.URLSearchParams ? new URLSearchParams(global.location.search) : null);
if (startParams && startParams.get('action') === 'new') {
  var ext = (startParams.get('ext') || '').toLowerCase();
  var doc;
  if (ext === 'md') {
    var n = 1;
    var used = Ed.docs.map(function (d) { return d.name; });
    while (used.indexOf('未命名-' + n + '.md') >= 0) n++;
    doc = Ed.createDoc({ name: '未命名-' + n + '.md', content: '' });
    doc.previewOn = true;
  } else {
    doc = newDoc();
  }
  Ed.activate(doc.id);
  if (doc.previewOn) updatePreviewVisibility(doc);
  // 清理 URL，避免刷新时重复新建
  if (global.history && global.history.replaceState) {
    global.history.replaceState(null, '', global.location.pathname);
  }
  return;
}
```
要点：
- 用 `URLSearchParams` 解析，安全支持空值/缺失
- md 分支命名走 `未命名-N.md` 计数器（复用 `uniqueUntitled` 思路），避免连点产生重名
- `previewOn=true` + `updatePreviewVisibility(doc)` 让预览面板自动展开
- `replaceState` 清空 `?action=...`，刷新不会反复触发

#### 2. `manifest.json` 第二个 shortcut 改名
- `name: "Markdown 预览" → "新建 Markdown 文档"`
- `short_name: "Markdown" → "MD"`

#### 3. `sw.js` 版本 v8 → v9
让已装 PWA 的 SW 拿到新 `app.js`。

### 验证（agent-browser + 真实 http 服务）
| URL | active.name | lang | previewOn | panePreviewHidden | previewTitle | btnPreviewOn | search |
|---|---|---|---|---|---|---|---|
| `?action=new&ext=md` | `未命名.md` | markdown | true | false | Markdown 预览 | true | "" |
| `?action=new` | `未命名-1.txt` | plaintext | false | true | 预览 | false | "" |

截图保存在 `.workbuddy/shot/test_md.png` 和 `test_new.png`。

### 几个坑
1. **Git Bash `python` 指向 WindowsApps 空壳**：`python --version` 无输出，`http.server` 不起来。要用托管 Python 完整路径 `/c/Users/Administrator/.workbuddy/binaries/python/versions/3.13.12/python.exe`，或者 `node` 起 `npx serve`。
2. **`background task` 启动服务器有时起不来**（输出为空）。可靠模式：`nohup python -m http.server 8874 --bind 127.0.0.1 >/tmp/srv8874.log 2>&1 & disown` 放在同一条 Bash 里 sleep + curl 自检。
3. **`agent-browser` eval 探测 `state` 会 ReferenceError**——`state` 是 `app.js` IIFE 闭包局部变量，没挂到 `window`。要从暴露的 `Ed` / DOM 元素（`#panePreview`, `#btnPreview`, `#previewTitle`）反推状态。
4. **`global.URLSearchParams`** 在所有现代浏览器都可用；用 `global.URLSearchParams ? ... : null` 兜底。
5. **（已纠正）`focus-existing` 启动模式**下点击快捷方式：
   - ❌ 旧结论（错误）：以为浏览器会导航已开窗口到 shortcut URL（重新加载）。
   - ✅ 实际情况：**窗口已存在时，浏览器不会导航/重载现有窗口**，而是通过 `launchQueue.setConsumer` 把 `params.targetURL` 投递到已运行的页面（`params.files` 为空、只有 `targetURL`）。原 `bootstrapInitialDoc` 只处理冷启动的 `location.search`，所以 warm launch 静默失效——这正是 #9 的根因。
   - 修复见下方【PWA Shortcuts warm launch 修复】。
6. **服务端测试要 `dangerouslyDisableSandbox: true`** 否则 curl 连不上 loopback 服务。

## 文件对比窗口的 WCO 让位

### 问题（用户 #10 反馈）
安装为 PWA 后打开「文本对比」窗口，工具栏右侧的「右 侧 (改) / 打开文件 / 粘贴 / 交换两侧 / 关闭」按钮被系统最小化/最大化/关闭按钮遮挡/挤在一起。

### 根因
`.diff-view` 是 `position: fixed; inset: 0; z-index: 60;` 的全屏覆盖层，盖住了 appbar；其顶部 `.diff-bar` 没有 WCO 让位，原 `padding: 8px 12px;` 让右侧按钮贴着视口右边缘，正好被系统按钮区域压住。

### 改动
套用 appbar 已有的模式（`env(titlebar-area-width, 0px)` + `env(safe-area-inset-right, 0px)`），只给 `.diff-bar` 加右侧让位：

```css
.diff-bar {
  ...
  padding: 8px calc(12px + env(titlebar-area-width, 0px) + env(safe-area-inset-right, 0px)) 8px 12px;
}
```

非 PWA 模式 `env()` 兜底 0px，视觉不变；PWA WCO 模式自动让出 ~140px 系统控件宽度。

### 关键修正（用户 #11 反馈）
第一版只改 padding、没改 `flex-wrap`，结果 `.diff-bar` 默认 `flex-wrap: wrap` 把右侧面板/按钮挤到第二、三行，浪费垂直空间。用户要求「按钮仍横向放在顶栏，只避让出右侧系统按钮的位置」。

修正：`.diff-bar` 加 `flex-wrap: nowrap;`（+ `min-width: 0;` 让 flex item 必要时可收缩），强制单行——所有按钮、面板仍在同一行，只是最右侧「关闭」按钮与视口右边之间留出 ~140px 给系统按钮。

### 不需要改
- `.diff-body`/`.diff-editor`/`.diff-overview` 不在顶部 36~44px 的系统按钮区域内（`.diff-bar` 已经占满该高度），无需额外让位。
- `.diff-overview`（最右侧 14px 差异滚动条）只有最顶端 ~36px 与系统按钮垂直重叠，但只是装饰性滚动条，无功能按钮，不影响使用，故不动。
- 不加 `overflow-x: auto`：diff 视图本来就需要较宽窗口并排比较；窄窗口下 flex item 收缩即可，避免引入横向滚动条这种新交互。

### 文件
- `css/diff.css`：`.diff-bar` 改 padding + `flex-wrap: nowrap` + `min-width: 0`。
- `sw.js`：`v10 → v11 → v12`（diff.css 已在 LOCAL_ASSETS，确保已装 PWA 拉到新样式）。
- `manifest.json`：不变。

### v13 迭代（用户 #12 反馈"再优化避让方式"）
v11/v12 是给 `.diff-bar` 加 `padding-right: calc(12px + env(...))`——把容器**整体**向右挤 140px，导致左/右面板与右文本窗的对齐位置都被压缩。用户希望：
- 左/右面板与原版一致（左靠左、右居中）
- 仅最右侧两个按钮（交换两侧、关闭）右边让位

**v13 方案**：去掉容器右 padding，改用 `::after` 伪元素做不可见的右占位：
```css
.diff-bar {
  padding: 8px 12px;   /* 还原，不带 env() */
  position: relative;  /* 让 ::after 绝对定位 */
}
.diff-bar::after {
  content: '';
  display: block;
  flex: 0 0 calc(env(titlebar-area-width, 0px) + env(safe-area-inset-right, 0px));
}
```

**为什么 work**：
- `::after` 是 flex 容器末位 item，`flex: 0 0 X` 固定基础宽 X、不 grow/shrink
- 两个 spacer 的可用空间 = 视口 - 24(padding) - 各 fixed 项 - X(伪元素)
- 两 spacer `flex: 1 1 auto` 等比平分剩余 → 中间视觉对称（与原版一致）
- 最右侧「交换两侧/关闭」按钮之后紧跟不可见 X 宽占位
- WCO 模式 X ≈ 140px（系统按钮宽度），tab 模式 `env()` 兜底 0px → X=0 行为不变

v14 加了 `--wco-right` 双保险，用户在已装 PWA 中测试说"无变化"。**根因找错了**——不是 env()，而是 SW cache-first 把 sw.js 自己锁死，浏览器永远拿不到新版 sw.js，更新检测不到 → 新 CSS 也进不了 cache。已装 PWA 永远跑旧 SW + 旧 CSS。

**v15 三处改动**：
1. **`sw.js` fetch handler 加 sw.js 自身 network-first 分支**（虽然浏览器对 sw.js 自带特殊处理不会通过 fetch handler，但加这层保险让意图明确 + 日后好维护）：
   ```js
   if (url.pathname === '/sw.js' || url.pathname.endsWith('/sw.js')) {
     e.respondWith(fetch(req).then(function (res) {
       if (res && res.ok) {
         var clone = res.clone();
         caches.open(LOCAL_CACHE).then(function (c) { c.put(req, clone); });
       }
       return res;
     }).catch(function () { return caches.match(req); }));
     return;
   }
   ```
2. **`activate` 给所有 client 发 `SW_UPDATED` 消息**：
   ```js
   }).then(function () { return self.clients.claim(); })
     .then(function () { return self.clients.matchAll({ type: 'window', includeUncontrolled: true }); })
     .then(function (clients) { clients.forEach(function (c) {
       try { c.postMessage({ type: 'SW_UPDATED', version: VERSION }); } catch (e) {}
     }); })
   ```
3. **`app.js registerServiceWorker()` 加 `SW_UPDATED` 监听器**，sessionStorage 去重，自动 reload 一次：
   ```js
   var SW_RELOADED_FLAG = 'webeditor_sw_reloaded_v';
   navigator.serviceWorker.addEventListener('message', function (e) {
     var d = e && e.data;
     if (!d || d.type !== 'SW_UPDATED') return;
     var v = d.version || 'unknown';
     var flag = SW_RELOADED_FLAG + v;
     if (sessionStorage.getItem(flag)) return;
     sessionStorage.setItem(flag, '1');
     location.reload();
   });
   ```

`sw.js` VERSION：`v14 → v15`。

**完整更新链路**：用户重开 PWA → 浏览器 fetch sw.js → 检测 v15 更新 → install → 预填 v15 cache → skipWaiting → activate → claim + postMessage SW_UPDATED → 客户端收到 → 自动 reload → fetch diff.css → 命中 v15 cache → 加载新版 CSS（带 var(--wco-right)） → 让位生效。

**关键经验**：
- **SW 自身必须 network-first 或不受 fetch handler 拦截**——cache-first 把 sw.js 锁死会让更新链路彻底失效。
- **SW update 后必须有客户端 reload 机制**——单 `clients.claim()` 只是接管但不重新加载资源；要在 activate 给 client 发消息，客户端监听后 reload。
- **用 `sessionStorage` 去重 reload 避免循环**：每个 VERSION 仅 reload 一次。

## 修复：PWA 概率卡在 CDN 探测/加载首页（17:52 次日报错）
症状：偶发打开 PWA 后永远卡在"正在探测/加载编辑器"启动页，Ctrl+R 刷新即正常。
### 根因
`js/loader.js` 的 `probeFastest()` 在探测到最快镜像后 `return res.text().then(resolve)`——先设 `settled=true` 再 await 读取响应体。
某些 CDN 会**先回响应头、再让响应体流停滞**：`res.text()` 永久 pending → 既不会 resolve 也不会 reject（全局 7s 定时器因 `settled` 已为真而不触发 reject）→ 整个启动 Promise 挂死 → 永远卡首页。刷新后重新探测此次体流完整，故正常。
### 改动
- `js/loader.js` `probeFastest()`：命中后**立即 resolve(url)**，不再 await `res.text()`；把读完体流改为后台 `res.text().catch(()=>{})` 尽力预热缓存、失败静默。
- `js/app.js` `boot()` 增加 45s **看门狗**：若 `app` 仍 hidden 则显示"加载超时+重新加载"按钮，杜绝极端网络下无入口的永久卡死；`startApp()` 进入编辑器与 `loadMonaco().catch` 失败路径均 `clearTimeout` 看门狗。
- `sw.js`：`v16 → v17`（loader.js / app.js 已在 LOCAL_ASSETS，确保已装 PWA 拉到新逻辑）。
### 验证
Node 单测模拟"响应头到、体流停滞(res.text 永不 resolve)"：修复后 `resolve` 在 1ms 触发、进程正常退出，无挂起；旧逻辑则永久挂死。
